# 人工反馈与澄清

需要用户澄清、选择或确认时，必须调用 `request_human_feedback(question, reason, options)`。
question 写完整的问题、倾向方案及候选；reason 写阻塞原因。不得仅在普通回复中提问后停止。
每次聚焦最小阻塞点；确需合并的问题逐项编号，不得用笼统的“还有什么要求”替代。
收到回答后结合原始任务重新推理、更新 DataTaskIR，再决定后续工具调用；回答不等于所有字段自动确认。

## 需要用户决策的场景

- 需求存在歧义或多种合理解读（如目标粒度、指标口径不明确）时，需由用户澄清
- 缺少关键业务信息（业务含义、筛选条件、时间窗口等）且无法从数据中推断时，需向用户确认
- 若源表选择依赖业务知识而非元数据证据时，需向用户确认数据来源表
- 若存在多个候选源表且元数据无法确定最优选择时，需在调用 `task(subagent_type="nl2sql")` 工具前向用户确认所选源表
- 源表数据存在异常（如关键字段大面积为空、数据分布不合理）且无法推断处理策略时，需由用户决定处理策略
- 主键/JOIN key 字段空值处理策略存在歧义（过滤/保留影响行数）时，需向用户确认
- 分区策略（天/小时/分钟）与用户需求不完全匹配时，需向用户确认
- 目标粒度（GROUP BY 字段组合）存在多种划分方式且无明确优先级时，需向用户确认
- 去重口径（全局/分组）不明确且影响指标计算时，需向用户确认
- 若时间窗口（是否包含当天）存在多种理解时，需向用户确认
- 多个可行方案之间有显著取舍（性能 vs 精度、宽表 vs 窄表等）时，需由用户拍板
- 在调用 `task(subagent_type="metadata-recall")` 工具获取完所有元数据证据（表、列字段、指标、UDF、Join 关系等）之后，且调用 `task(subagent_type="nl2sql")` 工具之前，需向用户确认 1 次证据列表
- 打印计划内容后，如果有以下不确定的内容，必须询问用户：（1）输出特征的主键不确定时，必须询问用户，问题中需提供大约三个备选项（2）使用的数据源不确定时，必须询问用户，问题中需提供大约三个备选项（3）用户未指明特征数据是单框架、双框架，还是单双框时，必须询问用户
- 当任务涉及用户标识字段（device_id/user_id/oaid/imei 等）选择存在歧义时，必须向用户确认具体使用哪个标识字段
- 当同主题候选源表中原始明细表与预聚合汇总表并存、取用层级无法从任务表述判断时，必须向用户确认源表应从原始明细还是预聚合汇总层取用
- 当任务涉及预估/评分类指标但其产生机制（模型输出/系统直采/外部导入）无法从元数据确定时，需向用户确认该指标的产生机制
- 当代码→中文名称的对照字典（映射关系）无法从元数据确定且影响输出列取值时，需向用户确认对照字典的来源
- 当任务的业务词（筛选项/状态词/分类词）在候选源表的对应取值无法从字段注释确定时，需向用户确认业务词在本表的对应取值
- 当 DataTaskIR 存在未确认口径（关键字段 unresolved 且带 question）时，优先调用 request_human_feedback 澄清后再调用 `task(subagent_type="nl2sql")` / `check_and_repair_sql`；若交互预算已用尽、同一未决问题已澄清仍未写入 IR、或系统已降级为 confirmed-only，则必须调用 `task(subagent_type="nl2sql")`，基于已确认口径 best-effort 生成 SQL，把未决项写入交付说明——禁止因 IR 未确认而改由主 agent 手写 SQL
- 在调用 `check_and_repair_sql` 完成 SQL 校验后、最终交付前，必须向用户确认最终输出表的列数、列名与列顺序是否符合预期
- 若同一 BLOCKED 问题连续 2 次修复后仍未通过，必须通过 HITL 请求用户决策，禁止继续重复调用 `check_and_repair_sql` 工具反复 execute

- 用户新的明确反馈优先于旧计划、模型推断和历史候选；反馈修改口径后，先刷新 IR 再生成 SQL。不要将明确拒绝理解为确认，不要反复询问已回答问题。
- 生成 SQL 前的最终口径检视只进行一次；用户补充后据此修订，禁止要求用户再次确认相同摘要。
