# SQL 需求变更修改 Skill

> **前置要求**：执行本 skill 前，必须先确认已阅读并遵守 instructions.md 中的通用规则，本 skill 不重复上述内容。

## 何时使用

- 用户要求在已有 SQL 上增加/删除/修改字段
- 用户要求调整 SQL 的业务逻辑（如更换 JOIN 表、修改过滤条件、调整聚合粒度等）
- 用户要求更换数据源表或调整分区策略
- 用户明确要求"改需求"、"增加特征"、"调整逻辑"

## 工作流
工作流必须完整执行 Step 1-6，变更说明和修改后的 SQL 文件都是必须交付物。

### Step 1: 理解变更需求

- 明确用户要改什么：新增字段、修改逻辑、更换表源、调整粒度等
- 识别变更影响范围：哪些 CTE/子查询受影响，是否涉及 JOIN 路径变更
- 如需求不明确，主动向用户确认

### Step 2: 查询元数据与规范

- 优先使用 `get_table_schema` 工具获取表、列信息
- 如需求变更导致源表不适用，使用 `metadata_recall` 工具查询相关的元数据、表等信息
- 通过 `read_file` 读取 sql_rules skill 中的 SQL 约束及规范

### Step 3: 确认并输出修改点

- 基于现有 SQL 确定需要修改的地方
- 修改原则：
  - **最小变更**：只改必要的部分，不重构无关节点
  - **规范合规**：变更部分必须符合 sql_rules 所有适用规则

直接在回复中输出待修改点，不需要写入文件。格式如下：

```markdown
# SQL 变更说明

## 概览
- 原始 SQL：{文件路径}
- 修改后 SQL：{文件路径}
- 变更原因：{用户需求描述}

## 变更清单

| # | 变更类型 | 变更位置 | 变更前 | 变更后 | 变更原因 |
|---|----------|----------|--------|--------|----------|
| 1 | 新增字段/修改逻辑/更换表源/调整粒度 | SQL片段位置 | 原始代码 | 修改后代码 | 对应需求 |
```

### Step 4: 修改并交付

- 根据 Step 3 生成的修改点修改 SQL
- 修改后对照 sql_rules skill 中的规则重新检查，确保未引入新问题
- 涉及表名列名时必须用 `get_table_schema` 验证
- 使用 `write_file` 写入修改后的 SQL 文件（命名规则见 instructions.md）
- 调用 `validate_deliverables` 校验
