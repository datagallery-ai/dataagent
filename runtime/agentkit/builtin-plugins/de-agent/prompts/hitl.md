业务澄清纪律（仅在 HITL 开启时生效）

1. 遵循 3 阶段交互模式：Initial 阶段确认数据源表；Mid 阶段确认用户标识字段和时间窗口口径；Final 阶段确认输出 schema。不要在 Initial 阶段就问输出格式，也不要在 Final 阶段才问数据源。
2. 收敛后提交优于反复试错：当元数据和用户确认已充分时，直接 submit SQL，不要反复 execute/validate 试错。连续 2 次 validate 失败后必须 HITL 而非继续重试。
3. 需求存在歧义或多种合理解读（如目标粒度、指标口径不明确）时，需由用户澄清
4. 缺少关键业务信息（业务含义、筛选条件、时间窗口等）且无法从数据中推断时，需向用户确认
5. 若源表选择依赖业务知识而非元数据证据时，需向用户确认数据来源表
6. 若存在多个候选源表且元数据无法确定最优选择时，需在调用 task(subagent_type="nl2sql") 工具前向用户确认所选源表
7. 源表数据存在异常（如关键字段大面积为空、数据分布不合理）且无法推断处理策略时，需由用户决定处理策略
8. 主键/JOIN key 字段空值处理策略存在歧义（过滤/保留影响行数）时，需向用户确认
9. 分区策略（天/小时/分钟）与用户需求不完全匹配时，需向用户确认
10. 目标粒度（GROUP BY 字段组合）存在多种划分方式且无明确优先级时，需向用户确认
11. 去重口径（全局/分组）不明确且影响指标计算时，需向用户确认
12. 若时间窗口（是否包含当天）存在多种理解时，需向用户确认
13. 多个可行方案之间有显著取舍（性能 vs 精度、宽表 vs 窄表等）时，需由用户拍板
14. 在调用 metadata-recall 子代理获取完所有元数据证据（表、列字段、指标、UDF、Join 关系等）之后，且调用 task(subagent_type="nl2sql") 工具之前，需向用户确认 1 次证据列表
15. 打印计划内容后，如果有以下不确定的内容，必须询问用户：（1）输出特征的主键不确定时，必须询问用户，问题中需提供大约三个备选项（2）使用的数据源不确定时，必须询问用户，问题中需提供大约三个备选项（3）用户未指明特征数据是单框架、双框架，还是单双框时，必须询问用户
16. 当任务涉及用户标识字段（device_id/user_id/oaid/imei 等）选择存在歧义时，必须向用户确认具体使用哪个标识字段
17. 当同主题候选源表中原始明细表与预聚合汇总表并存、取用层级无法从任务表述判断时，必须向用户确认源表应从原始明细还是预聚合汇总层取用
18. 当任务涉及预估/评分类指标但其产生机制（模型输出/系统直采/外部导入）无法从元数据确定时，需向用户确认该指标的产生机制
19. 当代码→中文名称的对照字典（映射关系）无法从元数据确定且影响输出列取值时，需向用户确认对照字典的来源
20. 当任务的业务词（筛选项/状态词/分类词）在候选源表的对应取值无法从字段注释确定时，需向用户确认业务词在本表的对应取值
21. 当 DataTaskIR 存在未确认口径（关键字段 unresolved 且带 question）时，优先调用 request_human_feedback 澄清后再调用 task(subagent_type="nl2sql") / check_and_repair_sql；若交互预算已用尽、同一未决问题已澄清仍未写入 IR、或系统已降级为 confirmed-only，则必须调用 task(subagent_type="nl2sql")，基于已确认口径 best-effort 生成 SQL，把未决项写入交付说明——禁止因 IR 未确认而改由主 agent 手写 SQL
22. 在调用 check_and_repair_sql 完成 SQL 校验后、最终交付前，必须向用户确认最终输出表的列数、列名与列顺序是否符合预期
23. 若同一 BLOCKED 问题连续 2 次修复后仍未通过，必须通过 HITL 请求用户决策，禁止继续重复调用 check_and_repair_sql 工具反复 execute

每次请求必须列出倾向方案和 1–2 个具体候选（表名、字段名、时间窗口或列数），禁止仅问“是否确认”。
真实用户答复、评测自动答复与系统兜底必须区分；预算耗尽或自动应答失败不能视为用户确认。
